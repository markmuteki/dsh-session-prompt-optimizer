# 提示词优化器

合成器工具行里的一个按钮。它把你已经打好的草稿改写成一条更清晰的指令，然后在输入框上方的对照卡片里并排展示——左边是你的原文，右边是改写。只有你点了「用这一版」，输入框才会被替换。

## 用法

| 操作 | 结果 |
| --- | --- |
| 单击 | 改写草稿，长度和结构尽量贴近原文 |
| Shift+单击 | 结构化改写：先目标，再背景与约束，最后是完成标准 |
| Alt+单击 | 压缩：意思不变，字数更少 |

按钮在模型 chip 左边；输入框为空、消息正在发送、或者上一次改写还没结束时，它会处于禁用状态。有改写结果在等你确认时，按钮显示对勾。

### 对照卡片

改写完成后，输入框正上方会展开一张卡片：

| 区域 | 作用 |
| --- | --- |
| 左栏「你的原文」 | 这次送去改写的原文，只读，方便逐句对照 |
| 右栏「优化后（可直接改）」 | 改写结果，是一个普通文本框，用之前可以随手再改 |
| 小标签 | 这次用的是哪个模式、参考了多少条历史消息 |
| 「用这一版」 | 把（可能已被你改过的）改写写进输入框，并关掉卡片 |
| 「复制」 | 只复制到剪贴板，输入框不动 |
| 「关闭」 | 关掉卡片，输入框不动 |

如果请求进行期间你又动过草稿，卡片会挂一个「草稿已改动」的提醒：你的新文字不会被悄悄覆盖。

## 改写会保留什么

- 草稿里已有的全部意图、事实、文件路径、名称、数字、版本和约束。优化器不允许凭空编出一条需求。
- 草稿的语言：中文还是中文，英文还是英文。
- 代码、命令、路径、URL 和引号里的字符串，逐字照抄。

它会去掉客套和铺垫，把任务本体提到最前面，把含糊的动词换成草稿显然想要的具体动作。本来就已经是条好提示词的草稿，几乎不会动。返回的只有改写结果：没有前言、没有解释、也没有整体包一层代码块。

## 它会先读一遍这个会话

写在一段进行中的对话里的草稿，通常不是自足的：「改一下那个按钮」如果不知道这场会话一直在说哪个按钮，就毫无意义。所以每次改写都会先拿到一小段它即将发言的那个会话：

- 最近的几条消息（最多六条，每条截到 600 字符，合计约 2400 字符）；
- 会话标题；如果有正在生效的目标，也带上目标；
- 这个会话运行的工作目录。

配给模型的规则很克制：把草稿里省略的指代补明确，沿用会话里已经确定的名称和决定，不许违背已经记下的约束；但不要复述、总结或回答这段历史。草稿本身已经说清楚时，这段摘要不改变任何东西。

这段摘要是只读的：插件不往会话里追加任何消息，除自己的缓存外不落盘，也只发给本来就会收到这条消息的那个模型。DSH 没有向插件开放跨会话的记忆服务，所以它是「本会话的历史 + 目标」，不是 Hindsight 记忆页，也不包含别的会话。

## 改写指令来自哪里

指令本身来自开源项目 [prompt-optimizer](https://github.com/linshenkx/prompt-optimizer) 的 `user-optimize` 模板，不是插件里手写的文本：

| 模式 | 模板 |
| --- | --- |
| 单击 | User prompt basic optimization |
| Shift+单击 | Step-by-step planning |
| Alt+单击 | Basic optimization 加一条精简规则 |
| `mode: "professional"`（仅接口） | Professional optimization |

harness 启动后不久会检查一次作者的最新 GitHub release，之后每六小时一次。有新版本时，会下载中英共六个模板、校验、缓存到磁盘，下一次点击就用新的。不安装任何东西、不需要重启；断网时继续用缓存，如果从来没有成功下载过，则回落到内置 prompt。

模板提供的是方法，插件会在它之上再叠自己的规则：草稿里的每一条要求、数字、名称、路径和验收标准都必须留下来——可以重排、合并重复，但不能为了「简洁」删掉条目；模式本身的形状也照样声明，所以结构模式仍然可以长到草稿的两倍，压缩模式则不许变长。输出预算按草稿长度和模型自身上限取（最多 16384 token），一旦撞到上限会先续写一轮，而不是把半截结果交给你。

缓存在插件旁边的 `.state/upstream.json`。`GET /_prompt-optimizer/health` 可以看到它正在跟随哪个 release，`POST /_prompt-optimizer/refresh` 可以立刻检查一次。校验不通过的那一批会被整体丢弃，所以上游改了格式也不会让插件停在半更新状态。

## 用哪个模型

用你输入框旁边那个模型，也就是这条草稿将来会提交给的那个模型，所以改写和真正执行的判断标准是一致的。取不到时会退到会话的 agent 选项，再退到 harness 的默认模型。推理档位钉在模型声明的最低档，免得思考预算把答案吃光。

## 限制

- **点「用这一版」才会替换整段草稿。** `setDraft` 写的是纯文本，会丢掉行内的引用 chip；一个指向文件的 chip 会变成该文件的 `@path` 文本。这也是卡片要先问一声的原因。
- 斜杠命令会被拒绝：改写它会把命令弄坏。
- 超过 12000 字的草稿会被拒绝。
- 同一个会话同时只跑一次；上一次还没结束时再点会被拒绝，而不是排队。
- 宿主 45 秒超时，前端 90 秒超时。

## 配置

没有需要你设置的项。插件在 harness 的 web 服务上挂三个同源路由——`/_prompt-optimizer/optimize`、`/_prompt-optimizer/health`、`/_prompt-optimizer/refresh`——并自行跟随上游版本。
